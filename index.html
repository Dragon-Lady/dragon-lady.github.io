Nightly transfers: close first, verify before completion

Transfer orchestration update · October 30, 2026

The nightly conversation-transfer workflow now separates scheduled transfers from software updates. It does not invoke the updater, wait for an installation password, or relaunch applications after transferring data.

Before a transfer, the runner checks peer availability, requests a graceful application shutdown, and confirms the applications are closed. If shutdown fails or an application reopens, the closed-app guards stop further work. Recovery copies and rehearsed merges protect the destination before live imports; unresolved conversation conflicts stop the pipeline before import.

Scheduling has two additional safeguards: a single-run lock prevents overlapping transfers, and a short overnight start window is checked again immediately before closing applications. A delayed invocation outside that window skips the transfer.

Completion now requires a comparison of conversation IDs and transcript hashes, plus Cursor room content, across the transfer endpoints. A successful upload alone cannot mark the transfer complete. Failed comparisons leave the run incomplete; the completed baseline is recorded only after verification passes.

Validation covers shutdown failures, unavailable peers, late starts, reopened applications and content mismatches. Disposable SQLite fixtures exercise Cursor's inline and chunked conversation formats, destination backups and transaction rollback.

This is an orchestration update, not a new PyPI or npm package release. Installing Twin Update, Raft Mover or Raft Ward does not enable this nightly workflow.

Twin Update

twin-update 0.5.3, released October 30, 2026
PyPI · Source · Release

Closes, updates and verifies the same apt-packaged desktop apps on two Linux machines in one run, with a verified one-command rollback. Built for Debian and Ubuntu-family desktops.

New in 0.5.3: two fixes to how leftover Cursor helpers are closed. Twin Update now checks again for Cursor's main process after each CPU sample, so if Cursor starts during the final sample, no helper is closed. And twin-update close-helpers --json now prints one valid JSON report and nothing else, whether the close goes ahead or is refused.

Upgrade with python -m pip install --upgrade twin-update==0.5.3.

Raft Mover

raftmover 0.1.2, released October 30, 2026
PyPI · Source · Release

A fail-closed handoff of closed SQLite chat databases, such as Cursor's, between two Linux machines. It uses Raft Ward to check that the apps that own the files are closed before it sends or adopts a frozen copy. It is a supervised prototype, and installing it does not set up a timer.

New in 0.1.2: Raft Mover no longer waits on Cursor's background agent worker. That worker never uses the files Raft Mover moves, but until now a move would not start while it was running. Raft Mover now turns on Raft Ward 0.1.5's owner_exempt = ["cursor-agent-worker"] by default, so a move can go ahead while the worker runs. Nothing else got looser. The Cursor editor and every other cursor-agent command still hold a move, and the worker still blocks one if it has a target file open or is moving files. If you prefer the old behavior, set owner_exempt = []. The README also adds a note: a terminal command or script that mentions an app's name counts as that app running. Raft Mover 0.1.2 needs Raft Ward 0.1.5 or newer.

Upgrade with uv tool install 'raftmover==0.1.2' --with 'raftward==0.1.5' --force or pip install -U 'raftmover==0.1.2'.

Raft Ward

raftward 0.1.5, released October 30, 2026
PyPI · Source · Release

Offline, read-only integrity checks for closed SQLite databases, frozen exports and backup folders. It looks for missing files, corruption, suspicious shrinkage, permission changes and signs of bulk encryption or renaming, and it does not change the files it watches. It skips a target while an app that owns it is running.

New in 0.1.5: an opt-in setting, owner_exempt = ["cursor-agent-worker"] (or gate(..., owner_exempt=["cursor-agent-worker"]) in the Python API), so Cursor's background agent worker no longer counts as a running Cursor app. The Cursor editor and other cursor-agent commands still do. An exempted worker is still checked for open target files and transfer activity. It is off by default, so existing setups work exactly as in 0.1.4.

Upgrade with uv tool install 'raftward==0.1.5' --force or pip install -U 'raftward==0.1.5'.

Twin Update

twin-update 0.5.2, released October 30, 2026
PyPI · Source · Changelog

Closes, updates and verifies the same apt-packaged desktop apps on two Linux machines in one run, with a verified one-command rollback. Built for Debian and Ubuntu-family desktops.

New in 0.5.2: leftover Cursor sandbox helpers are checked before closing, so by default they no longer cause a 90-second close timeout. Only helpers that are clearly idle get closed, with one SIGTERM and never SIGKILL. Anything active or unknown is left alone. A new twin-update close-helpers command runs the same check on one machine from your own terminal, and new optional [close] settings tune it.

New in 0.5.0: ChatGPT desktop can use the same optional snapshot hook as Cursor. It is off until you set raft.chatgpt_dbs (the older raft.chatgpt_db key still works), and files are copied only while ChatGPT is closed. ChatGPT is still updated when it is open, then left closed. 0.5.1 changes nothing in the tool; it lets an update that did not finish run.

Linux Supply Chain Guard

linux-supply-chain-guard 0.6.3, released October 30, 2026
npm · Source · Release

A read-only Linux host checker for supply-chain incident response, covering vulnerable kernel posture, risky module state and known developer-tooling persistence indicators.

New in 0.6.3: a read-only check for kernel issue CVE-2026-98432. It compares the running kernel with the first fixed stable release on the 7.2, 5.15 and 5.10 branches (7.2.10, 5.15.223 and 5.10.272); other branches say "unknown, check vendor." The CVE record also lists fixes for 6.1.190, 6.6.159, 6.12.113 and 6.18.56, and mainline 7.3; this release reports those branches as "unknown, check vendor." It also tells you when a reboot is pending, because a fixed kernel only counts once it is the one running. It makes no network calls and does not test the bug.
